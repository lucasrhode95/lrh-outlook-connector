# Outlook Connector Roadmap

Open decisions, implementation, fixes and validation only. Completed behavior belongs in the
requirements and architecture; completed live evidence belongs in the research record.

Snapshot **2026-10-14**.

## Decisions

- **Default conversation scope.** `get_conversation` leaves out Deleted Items and Junk Email unless `scope.deleted_items=true`, the same default as listing and search. A conversation can therefore look shorter than it does in Outlook. Example: you reply to a thread and then delete the original; `get_conversation` returns only your reply, and the original appears with `scope={"deleted_items": true}`. Confirm this default, or include deleted mail in conversations by default, since a conversation is usually read for its whole history.

## Enhancements

- **Passive HTML is a deny-list.** Draft bodies and signatures pass one checker, [`passive_html.py`](../src/outlook_connector/service/passive_html.py), which refuses what it names: scripts, frames, form controls, event-handler attributes, `javascript:` and `vbscript:` URLs, elements that change how later markup is read, and unfinished markup. Anything it does not name passes. It also reads markup with Python's HTML parser, not a browser's, so markup the two tokenize differently could pass. Example: malformed markup that Python reads as an attribute value but a browser reads as a new tag with an event handler. The one save test ([research §3.20](api-research.md#320-unfinished-markup-on-save-2026-10-13)) showed Outlook dropping an event handler, but that is one account and one client. Candidates: an allow-list of elements and attributes (for example `p`, `div`, `span`, `table`, `a href`, `img src`, inline `style`), or wider evidence of what Outlook strips, checked against browser parsing.
- **Event to Teams meeting chat.** `get_calendar_event` returns a Teams join link but no Teams chat id, and Search v2 event fields expose none either ([research §3.16](api-research.md#316-live-outlook-connector-mcp-calendar-check-2026-10-12)). Example: after finding "Project Alpha weekly sync" here, the agent has to look up the meeting chat in the Teams connector by name and time itself. An automatic handoff (event → chat id → Teams messages) first needs a supported Teams-side lookup from the event or its join link to the chat; reading an id out of the join URL is not established. Transcript and recap discovery stay in the [Teams roadmap](https://github.com/lucasrhode95/lrh-teams-connector/blob/main/docs/roadmap.md).
- **Calendar profile.** Calendar windows read Graph through the shared `teams.graph` profile, because the Outlook Graph profile (`outlook.graph`: `Mail.Read`, `User.Read`) has no calendar scope. Outlook calendar reads therefore depend on a profile named and shaped for Teams. Example: if the Teams profile changes its client or drops its calendar scopes, `list_calendar_events` falls back to Outlook Web and loses descriptions, `contains` and `include_body`. Options: a purpose-named calendar profile in `lrh-m365-auth` on the same client and resource ([research §3.17](api-research.md#317-calendar-range-listing-and-description-search-through-the-teams-client-graph-profile-2026-10-12)), or `Calendars.Read` on `outlook.graph`, whose preauthorization for that first-party client is untested and may fail with `AADSTS65002` ([research §3.13](api-research.md#313-calendar-event-search-through-graph-and-the-calendar-permission-2026-10-10)).
- **Graph-first event hydration.** `list_calendar_events` reads Graph first, but `get_calendar_event` reads through Outlook Web (`GetItem`) only. Hydrating through Graph (`GET /me/events/{id}`) would put listing and details on the same service, with the same plain-text descriptions, and keep Outlook Web as the fallback. One Graph read of an event's subject and description worked ([research §3.17](api-research.md#317-calendar-range-listing-and-description-search-through-the-teams-client-graph-profile-2026-10-12)); the other detail fields (attendees, response status, join link, attachment metadata) and the id conversion need their own check.
- **Graph event search.** `search_calendar_events` uses Search v2, which takes no date restriction and cannot page past offset 1,000, so date questions go to `list_calendar_events`. Graph Search (`POST /search/query` with `entityTypes=["event"]`) returned 12 hits in one page for a known description term ([research §3.17](api-research.md#317-calendar-range-listing-and-description-search-through-the-teams-client-graph-profile-2026-10-12)). Unverified: whether it restricts dates on the server, and whether a query can target the description alone. Example: if it accepts a date restriction, "budget review in the week of 2 November" could be one ranked search limited to that week. Until then, Search v2 stays the topic search.
- **Other calendars.** Only the signed-in user's default calendar is listed and searched. Secondary calendars the user created, calendars shared with them and colleagues' calendars are out of reach. Example: "What is on the Project Beta team calendar next week?" or "What does Alex have on Thursday?" cannot be answered. The `teams.graph` token already carries `Calendars.Read.Shared` ([research §3.17](api-research.md#317-calendar-range-listing-and-description-search-through-the-teams-client-graph-profile-2026-10-12)); reading shared or delegated calendars with it is untested ([research §3.18](api-research.md#318-list_calendar_events-live-check-2026-10-12)).
- **Event attachment download.** `get_calendar_event` lists attachment metadata (name, type, size, inline flag), but nothing downloads the content: `download_attachment` takes a mail `message_id`, and its Graph route is message-scoped ([research §3.16](api-research.md#316-live-outlook-connector-mcp-calendar-check-2026-10-12)). Example: an agenda PDF attached to a meeting is visible by name, but the agent cannot read it. An event-scoped download route has not been tested.
- **Branch-aware conversations (parked).** A conversation is exactly Exchange's conversation: one flat list, oldest first, with nothing saying who answered whom. Example: Alice sends a proposal, Bob replies to all, and Carol forwards it to Dan, who replies to Carol; if Exchange groups all four, `get_conversation` returns them by date, and Dan's reply reads as if it answered Bob. Plan: build the reply tree from RFC 5322 `Message-ID` / `In-Reply-To` / `References` headers, with Exchange `ConversationId` and `Thread-Index` as supporting evidence; detect branches, including forwards; and offer a merged chronological view where each message is labeled with its branch. Check the quality of those headers in real mail first.

## Validation

- **Fresh-account consent.** The `m365.search` and `teams.graph` calendar grants were verified on one account only. Check them on a new account before relying on them.
- **Mail search route.** Graph Search API has not been compared with the current Graph `$search` route on identical queries ([research §3.15](api-research.md#315-outlook-mail-search-timing-and-route-comparison-2026-10-10)). Compare terms, limits, hydration, request counts and latency before considering a change.
